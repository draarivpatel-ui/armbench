# ArmBench

An image and video workload bench for Arm. It times real kernels on the local Arm CPU in your browser, then places those readings beside cloud figures that are always labeled as estimates. Built by Aariv Patel as an entry for the OpenCV AI Competition 2026.

## Honesty Statement, Read This First

AWS Graviton was not used. No cloud instance was contacted at any point. The local measurements in this repository were taken on an Apple Silicon Mac (Arm64, Armv8 and Armv9), which is a genuine Arm CPU but not the AWS Graviton target. Local Arm measurements stand in for cloud figures, every cloud figure is an arithmetic estimate carrying an Estimate badge with its assumptions listed, and no estimate is ever presented as a measurement. Section 3 of the Environment Card panel and the README section below document the exact plug in point for rerunning the identical suite on an EC2 Graviton instance.

## What It Is

A static single page app, `index.html` at the repo root, with four panels:

1. **Workload Bench** runs real in browser timing of five image kernels (bilinear resize, grayscale, 3 by 3 box blur, Sobel edge detection, 256 bin histogram) plus a synthetic 8 frame video pipeline, across image sizes and iteration counts, using seeded deterministic pixel buffers and a monotonic clock. The host specs and the seeded test pattern are shown next to the results.
2. **Baseline Compare** sets the measured local numbers beside estimated Graviton figures in a table and a canvas chart. Solid cells are measurements. Hatched, dashed cells carry the Estimate badge and are projections from a documented model, never measurements.
3. **Environment Card** states plainly what machine was measured, what was not measured, and how to reproduce on Graviton.
4. **Report Export** generates a copyable methodology block, including the honesty statement, the assumptions and the exact reproduction commands, so a judge can rerun everything.

## Quick Start

The page uses module scripts, so it needs a static server rather than a double click:

```sh
python3 -m http.server 8000
# then open http://localhost:8000
```

Any static server works. There is no build step and nothing to install.

Run the same suite without a browser:

```sh
node scripts/run-bench.mjs                          # table, all sizes
node scripts/run-bench.mjs --seed 1337 --iterations 5 --all-sizes
node scripts/run-bench.mjs --size 512 --json        # machine readable
```

Run the tests (48 assertions, Node 18 or newer, no packages, no network, about 2 seconds):

```sh
node --test tests/
```

## Methodology

- **Input.** A deterministic grayscale pattern (diagonal gradient, lifted disc, seeded noise) generated by a Mulberry32 seeded PRNG. The same seed produces identical bytes in the browser, in Node and on any machine, so every run processes identical input.
- **Timing.** One warmup call per workload runs uncounted, then exactly the requested number of iterations is timed with `performance.now`. The page reports mean, median and throughput; the harness supports an injectable clock so tests verify the statistics deterministically.
- **Budget guard.** A timed pass never processes more than 12 million pixels. Iterations are clamped per workload and size, so a full run stays under roughly ten seconds on a laptop Arm CPU.
- **Kernels.** Plain JavaScript loops over `Uint8ClampedArray` buffers, single threaded, one implementation shared by the browser and Node (`js/armbench-core.js`). The box blur replicates edges and divides by 9 on every window; Sobel runs on a luma plane with clamped borders; resize is bilinear with floor half dimensions.

## Estimate Model

Every cloud figure comes from this arithmetic, applied to a local measurement:

```text
estimate = local ops/sec x 0.8125 (clock) x 0.75 (memory) x 1.0 (cores)
```

- **Per core clock scaling:** 2.6 GHz Graviton3 public spec clock over an assumed 3.2 GHz Apple Silicon performance core gives 0.8125. The spec figure is approximate.
- **Memory bandwidth heuristic:** a per-core share of 0.75 reflects that socket bandwidth on a many-core server is divided across more cores than on an 8 to 16 core laptop. Heuristic, not measured.
- **Core count:** factor 1.0. The reference kernels are single threaded, so core count is deliberately not applied.
- **Known limits:** the estimates ignore microarchitecture, cache hierarchy, SIMD width, compiler flags, operating system and thermal behavior. They are order of magnitude planning figures only.

## Graviton Plug In Point

On any AWS Graviton instance (Amazon Linux 2023, c7g family, Node 18 or newer, zero packages to install):

```sh
node scripts/run-bench.mjs --seed 1337 --iterations 5 --json
```

The same command, the same kernels and the same seed produce the same table on the cloud CPU. Paste the local results and the Graviton output side by side; the honesty rules hold unchanged, because the Graviton numbers become measurements on that machine and everything else stays labeled exactly as before.
